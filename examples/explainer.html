What a canceled class does to somebody's money

A booking is a receipt for a promise. Breaking the promise does not tear up the receipt.

Cancel a class with "refund everyone" ticked and the money stays where it is. The screen says it started refunding; twelve minutes later the order is still paid. Reproduced on four classes across two runs.

Everything below explains why that is possible — and why the same cancel can also tell you there is nothing to refund when there is.

An order and a class are two different things that only look joined.

A class is a session on a date. An order is somebody's purchase, and it holds the seats they booked. The order sits inside the class, and each seat sits inside the order.

An order can only ever be made on a class that is live — draft, started, ended, canceled and postponed all refuse it, and once one order exists the class can no longer be unpublished. So every case below is an order taken while the class was live that then had the class move underneath it.

That nesting is why a class can move without the money moving. Canceling changes the state of the outer box. Nothing about that automatically reaches the money in the innermost one — something has to walk down and touch it.

Pressing cancel starts four things. Only three of them finish.

The button does not refund anybody itself. It sets the class's state and hands the refunding to a separate job, and that job is where the money is lost.

The class turns canceled
Immediate, and it sticks. Every screen that reads the class's state updates.
It counts who is owed
Answers with a number — one order to process — and hands back a job name to watch.
The refunding job runs
Reports that it started. Twelve minutes later the order is untouched and still reads paid. This is the step that never lands.
The customer gets told
The confirmation email still points at the class's public page — which now answers "not found".

Refunding the same order by hand works, including after the cancel. So nothing is wrong with refunding — what is wrong is the job the cancel hands it to. All of this is front-desk money: cash, comp and paid-elsewhere. The card path was deliberately not driven, so real card refunds are untested in both directions.

The same cancel can also say there is nothing to refund.

Two kinds of order make it answer "no orders" — a class carrying real unrefunded money reporting that it has none.

An order already partly refunded
Someone gave back one seat of four. The remaining three are still paid for, and the count skips the order entirely.
A comp
Nothing to give back, correctly — but it is counted the same way as the case above, so you cannot tell them apart from the answer.
Two states that could not be tested at all
Unpaid and disputed have no way in from the admin, so ten of the squares are honestly marked not run rather than guessed at.

The revenue on the orders screen is not calculated here.

The admin asks the server for the totals and prints what comes back, word for word. When the number is wrong, it is wrong before it arrives.

Attendees is the exception. The server sends no total at all, so the admin adds up the rows itself — which is why one of the two cases below is fixable here and the other is not.

The customer's link dies with the class.

A canceled class's public page answers "not found". A postponed one still loads, and so does a live one. The link in the confirmation email is the one the customer clicks when they want to know what happened — and it is the one that breaks.

Postponed behaves correctly. Canceled is the only state that takes the page away, at exactly the moment somebody needs to read it.
